Product Document · v0.2

站内信：把该说的话，送到该看到的人

现有「文章」只能面向所有人发布公开内容，无法对某个用户说一句具体的话，也没有已读状态。站内信要补齐这条能力：用消息模板 + 变量生成带用户上下文的短提醒，例如「您的宠物小白饿了，快去喂食」，并把未读、已读、跳转和过期管理起来。本期只做中文、Web 与管理后台，移动端后续接入同一套消息。

版本 v0.2（范围已确认） 端 Web、管理后台 语言 中文 目标用户 学生（接收）、运营与内容人员（发送） 依赖 用户资料、宠物状态、现有登录态与后台权限

1. 背景与问题

产品里已经出现三类需要主动告知用户的事件，但当前没有承载渠道：

  • 宠物状态变化：饱腹度过低时，用户只有主动打开宠物页才会发现，错过喂食时机。
  • 系统运营事件：版本升级、维护窗口、功能上线，缺少一个能触达已登录用户的固定位置。
  • 账号与学习提醒：未来需要提醒连续未学习、资料未完善等，目前只能靠页面内的静态提示。

这些场景的共同点是：内容很短、必须指向具体用户、需要知道用户看没看、往往还要一跳直达。文章是公开的长内容，既没有收件人，也没有已读状态，放在文章里会让公开列表混入私信，因此不复用文章模型。

产品决策

  • 建立独立的「消息中心」，作为所有主动通知的唯一入口。
  • 消息内容必须来自「消息模板」，通过 {$变量名} 占位符生成个性化文案。
  • 消息只做短提醒：标题 + 正文 + 可选跳转；长内容仍由文章承载，消息只负责把人带到文章。
  • 用户侧统一管理未读与已读；后台统一管理模板、全站广播发布与撤回。

预期可观察结果：用户登录后能在固定入口看到未读提醒，点击后直达对应页面；运营修改文案只需编辑模板，不需要发版。

2. 与文章模块的边界

两者是「公开内容」与「用户消息」的关系，不做合并
维度文章站内信
面向对象所有访客，公开可读具体用户，只有本人可见
内容形态富文本长内容、分类、频道短标题 + 短正文 + 跳转
状态草稿 / 已发布草稿 / 已发布 / 已撤回 / 已过期，另有每人未读与已读
生命周期长期存档，可反复编辑有生效期与过期时间，事件消息需要去重
复用方式作为消息跳转的目标页通过跳转配置指向文章详情，不共享内容结构

结论：站内信独立建模。文章详情可以作为消息的落地页，但消息不复制文章的分类、富文本与浏览量体系。

3. 目标与范围

目标

  • 用户能在 Web 的固定入口看到未读消息，并能区分「未读 / 已读」。
  • 用户不能删除消息，避免误删后无法找回；消息只在过期或撤回后从列表消失。
  • 一条模板可以生成多条个性化消息，模板改动不影响已发出的历史消息。
  • 运营可以独立完成「建模板 → 预览 → 发布全站 → 撤回」，不需要研发介入。
  • 系统事件（如宠物饥饿）按规则自动生成，同一事件不重复打扰。
  • 任何消息都不会因为变量缺失、跳转失效或权限问题而展示出原始占位符或错误页面。
P0 完成「模板 → 发布 → 接收 → 已读」的完整闭环；P1 做移动端接入与推送增强
层级内容说明
P0Web 消息中心、未读数、已读 / 全部已读、消息模板管理、变量占位符、实时预览、测试发送、全站广播、生效与过期、宠物饥饿消息、系统升级公告、后台消息列表与撤回、权限与审计构成完整闭环
P1移动端消息中心（复用同一套消息与已读状态）、定时发送、消息分类筛选、App 系统推送扩展触达端与运营能力
不做用户删除消息、定向人群发送、英文 / 多语言模板、聊天与回复、附件与图片消息、短信 / 邮件 / 微信触达、富文本长文与本期“中文、Web、全站广播 + 事件触发”的定位无关

4. 产品模型

4.1 对象定义

对象定义关键约束
消息模板一组可复用的标题、正文与跳转配置，用变量适配不同用户和事件编码全局唯一；被消息引用后不可删除，只能停用
模板变量模板中声明的占位符，如 pet_name，运行时替换为真实值必须先声明后使用；区分全局变量与用户变量
消息一次发送产生的通知记录，保存渲染后的标题、正文和变量快照发送方式为全站广播或事件触发；发布后内容不可编辑，可撤回
用户消息状态某个用户对某条消息的未读、已读状态每个用户独立，互不影响；用户不可删除
消息事件触发消息生成的业务事件，如宠物饥饿、系统升级按去重键保证同一事件只生成一次

4.2 消息类型

类型发送方式触发源典型场景默认级别
系统全站广播运营手动发布版本升级、维护通知、功能上线重要
宠物事件触发宠物状态变化宠物饥饿、长时间未喂养提醒
学习事件触发（P1）学习数据变化连续未学习、目标未完成普通
账号事件触发（P1）账号事件资料待完善、密码变更普通

4.3 模板变量

模板变量分为两类，用于在后台校验「这条模板能不能发给全站」：

作用域含义示例可用于全站广播
全局变量所有用户取值相同site_name、latest_version、upgrade_time可以
用户变量每个用户取值不同nickname、pet_name、pet_satiety不可以，只能用于事件触发消息

每个变量需声明：变量名、显示名、类型（文本 / 数字 / 时间）、作用域、是否必填、示例值、缺省值。变量名只允许字母、数字与下划线。

4.4 状态与生命周期

模板：启用→ 停用（不可删除）
消息：草稿→ 已发布→ 已过期 / 已撤回
用户侧：未读→ 已读（不可删除）
  • 模板停用后不可用于新消息，已发出的历史消息不受影响。
  • 消息发布后不可编辑标题、正文与变量；如需修正，撤回后重新发布。
  • 撤回后所有用户不再看到该消息，已读记录保留用于审计。
  • 过期消息不再下发、不在列表展示，后台仍可查询。

5. 功能需求

FR-01

消息中心入口与未读数

目的：让用户在不主动寻找的情况下知道「有事发生」。

项目规则
入口两个入口指向同一页面：① Web 导航栏右上角铃铛；② 个人中心左侧导航的「消息」，位于「设置」上方。本期不提供移动端入口
可见性仅登录用户可见；未登录不展示铃铛与红点，个人中心左侧导航也不展示「消息」
登录要求消息列表与详情都属于个人中心页面，必须登录后访问；未登录直接打开链接时跳转登录页，登录后回到原消息
未读数未读数 = 已发布 + 未过期 + 无已读记录的消息数
红点未读数大于 0 时显示数字，超过 99 显示「99+」；等于 0 时不显示
更新时机登录后加载一次；打开消息中心、标记已读、全部已读后刷新；页面重新获得焦点时可刷新
异常未读数请求失败不阻塞页面，红点保持上一次结果，不弹错误提示
FR-02

消息列表与筛选

目的：让用户快速扫到最重要、最新的提醒。

  • 页面沿用个人中心外壳：左侧为现有导航（个人信息 / 我的教材 / 我的宠物 / 学情分析 / 我的收藏 / 错题本 / 消息 / 设置），「消息」位于「设置」上方并保持选中。
  • 默认排序：未读优先，其次按发布时间倒序。
  • 筛选：全部 / 未读。
  • 列表项展示：标题、正文摘要（最多两行）、类型标签、发布时间、未读圆点、可选跳转按钮。
  • 空态：全部为空时提示「暂无消息」；未读筛选为空时提示「没有未读消息」。
  • 分页：Web 每页 20 条，分页加载。
  • 消息不提供删除操作，列表项不出现删除按钮或滑动删除。
  • 进入列表不会自动把消息标记为已读。

FR-03

消息内容与跳转

目的：让用户在读完一句话后能立刻处理。

项目规则
详情形态Web 铃铛下拉展示最近 5 条 + 「查看全部」；完整列表与详情都放在个人中心外壳内，左侧导航保持可见且「消息」选中
正文长度建议不超过 200 字；超出时详情页滚动展示，列表只显示两行摘要
跳转类型无跳转 / 站内页面 / 外部链接
跳转行为点击「去处理」或消息主体时先标记已读，再跳转；无跳转的消息只标记已读
权限校验跳转前校验目标是否对当前用户可见；目标不存在或无权限时停留在消息详情并提示「内容已失效」
安全站内路径必须以 / 开头；外部链接只允许 http 或 https；不允许多层重定向
FR-04

已读与全部已读

  • 单条已读：用户点击消息或进入详情时写入已读时间；重复点击不报错。
  • 全部已读：只影响当前用户的全部未读消息；执行前不需要二次确认。
  • 用户不能删除消息；消息只在过期或撤回后从列表消失，历史已读状态保留用于统计。
  • 不提供「标记未读」操作，避免未读数被反复修改。
  • 已读状态按用户隔离，同一设备切换账号后互不串数据。
FR-05

消息模板管理

目的：让运营用一套结构管理所有通知文案，避免每次改字都发版。

模板字段

字段必填规则
模板名称是给运营看的中文名，允许重复
模板编码是全局唯一，创建后不可修改；只允许小写字母、数字与下划线，如 pet_hungry
消息类型是系统 / 宠物 / 学习 / 账号
消息级别是普通 / 提醒 / 重要；只影响展示样式，不改变排序
发送方式是全站广播 / 事件触发；决定可用变量范围与是否需要去重键
标题模板是纯文本，最长 40 字，允许使用变量
正文模板是纯文本，最长 500 字，允许使用变量；不支持 HTML
跳转配置否无 / 站内页面 / 外部链接；站内页面可带变量
去重键条件必填发送方式为事件触发时必填，如 pet_hungry:{$pet_id}:{$date}；同一去重键只生成一条消息；全站广播不配置
变量声明否声明模板中使用的全部变量及其作用域、必填与示例值
启用状态是启用 / 停用；停用后不可用于新消息

模板校验

  • 标题与正文中出现的每个 {$变量名} 都必须在变量声明中存在，否则禁止保存。
  • 声明了但未使用的变量给出警告，不阻止保存。
  • 全站广播模板不允许使用用户级变量；保存时直接阻止，并提示删除变量或改为事件触发模板。
  • 事件触发模板必须配置去重键，且去重键只能使用已声明变量。
  • 模板编码被历史消息引用后不可删除，只能停用。
  • 删除未被引用的模板需要二次确认。
FR-06

变量语法与渲染规则

目的：让「您的宠物{$pet_name}饿了」在不同用户、不同事件下都能得到正确文案，且失败时不会露出占位符。

规则说明
占位符语法{$变量名}，变量名只允许字母、数字、下划线
取值来源全站广播由运营填写全局变量；事件触发由系统按事件上下文自动填充用户变量
纯文本变量值一律按纯文本处理，不解析 HTML 或 Markdown，避免脚本注入
长度限制单个变量值最长 50 字，超出截断并标记；截断后仍保证语句通顺
必填缺失不发送该条消息，在后台记录失败原因，不允许用空值发布
非必填缺失使用模板中配置的缺省值；没有缺省值则替换为空字符串，并去掉因此产生的多余空格
未知变量渲染阶段遇到未声明变量视为错误，整条消息不发送，绝不把 {$x} 原样展示给用户
发送快照消息保存渲染后的标题、正文、跳转地址与变量值快照；之后修改模板不影响已发消息
变量回显后台详情可查看本条消息当时的变量值，便于排查文案问题

FR-07

模板预览与测试发送

  • 编辑模板时提供实时预览，使用运营填写的示例值渲染标题与正文。
  • 预览必须与真实消息使用同一套渲染规则，避免「预览正常、发出乱码」。
  • 支持「发送测试消息」：由运营指定一个 App 测试用户账号接收，只发给该用户，不进入正式统计，不影响其他用户。管理员账号与 App 用户账号是两套体系，测试消息必须落在 App 用户侧的消息中心才能验证真实效果。
  • 测试消息在标题前标记「测试」，有效期 1 天，过期后自动不可见。
  • 变量缺失时预览仍展示渲染结果，同时在预览下方提示缺失项，阻止正式发布。
FR-08

消息发布（全站广播）

目的：让运营用最少步骤把系统消息发给全站用户。

项目规则
发布来源P0 必须选择一条「全站广播」类型且已启用的模板；不支持在发布页直接改文案，避免模板与消息两套内容
发送范围固定为全站用户，不提供指定用户或多选用户；事件触发消息由系统生成，不在发布页手工创建
变量填写只允许全局变量；存在必填变量未填写时阻止发布
发布时间P0 仅支持立即发布；定时发送为 P1
过期时间可选；不填则长期有效，建议系统类消息设置 7 天 [假设]
发布前确认展示渲染后的标题、正文与可见范围（全站用户），运营确认后发布
发布结果成功提示「已发布全站」；变量缺失或模板停用时拒绝发布并说明原因

全站消息不预先为每个用户生成一条记录，用户打开消息中心时取到消息，再用各自的已读状态渲染。

FR-09

宠物饥饿消息

目的：在宠物真正需要照顾时提醒一次，不制造焦虑、不反复打扰。

项目规则
触发用户打开宠物页或消息中心时，系统按当前饱腹度与最近喂养时间计算宠物状态
发送方式事件触发，只发给该宠物的主人，不做全站广播
生成条件宠物已领养、饱腹度低于 30、最近 2 天内有喂养记录（即「饥饿」而非「沉睡」）
模板固定使用 pet_hungry 模板：「您的宠物{$pet_name}饿了，快去喂食。」
去重同一只宠物同一天最多生成 1 条；去重键包含宠物与日期
免打扰仅在 08:00–22:00 生成；夜间不新增消息，次日再判断 [假设]
状态恢复用户喂食后不再新增；已生成的消息保留，用户已读后自然消失
边界未领养、宠物已删除、饱腹度正常时不生成；同一用户多只宠物时按宠物分别去重（P0 每人 1 只）
跳转站内宠物页；跳转失败时提示「宠物信息已更新，请刷新后重试」
FR-10

系统升级公告

  • 运营选择 system_upgrade 模板，填写全局变量：最新版本号、升级时间、更新说明链接。
  • 固定为全站广播，不提供指定用户发送。
  • 消息级别默认为「重要」，在列表中排在普通消息之前（同为未读时按发布时间倒序）。
  • 建议设置过期时间，避免升级完成后用户仍看到旧公告 [假设：默认 7 天]。
  • 更新说明链接可指向文章详情；消息本身不承载长文。
  • 升级时间变更时，撤回旧消息后重新发布，不直接编辑已发消息。
FR-11

后台消息列表与撤回

项目规则
列表字段标题、模板编码、类型、级别、发送方式、状态、发布时间、过期时间、已读人数
筛选按类型、状态、发送方式、模板编码、发布时间范围、标题关键词
详情查看渲染后的完整内容、变量快照、失败原因、已读人数
撤回仅「已发布」可撤回；撤回需二次确认；撤回后所有用户不可见，已读记录保留
复制可基于历史消息复制一条新草稿，重新填写变量与时间

6. 共享规则

6.1 未读、已读与可见性

条件是否计入未读是否在列表展示
消息已发布且在生效期内是（无已读记录时）是
已过有效期否否
已撤回否否
用户已读否是（置灰展示）

6.2 去重与频控

  • 事件型消息必须配置去重键；同一去重键只生成一条消息，重复触发直接跳过。
  • 宠物饥饿默认按「宠物 + 日期」去重，每天最多一次。
  • 同一模板的全站消息，同一天重复发布需二次确认，避免误操作造成刷屏。

6.3 过期与保留

  • 过期消息不再生成、不再下发、不在用户列表展示，后台仍可查询。
  • 已过期或已撤回的消息保留 90 天用于审计与问题排查（已确认）。
  • 用户的已读记录随消息保留期清理，不单独长期保存。
  • 用户侧没有删除能力，消息记录在保留期内始终可查。

6.4 文案与内容规范

  • 标题不超过 40 字，正文不超过 500 字；列表只展示正文前两行。
  • 标题不使用「紧急」「最后通知」等制造焦虑的措辞；宠物类消息保持轻松语气。
  • 正文不包含手机号、身份证、完整账号等敏感信息。
  • 变量值来自用户资料或宠物资料时必须原样展示，不做二次拼接，避免语句歧义。
  • 仅支持中文文案，暂不做英文；模板与消息字段不设语言维度。

8. 数据表结构

沿用现有 Prisma + Supabase Postgres 约定：主键使用 BigInt 自增，用户主键为 String，状态字段使用 String 而不是数据库枚举，时间统一使用 DateTime。新增三张表，不改动现有文章与宠物表。

8.1 NotificationTemplate（消息模板）

model NotificationTemplate {
  id                  BigInt   @id @default(autoincrement())
  code                String   @unique @db.VarChar(60)   // pet_hungry
  name                String   @db.VarChar(80)
  type                String   @db.VarChar(20)            // system | pet | study | account
  level               String   @default("info") @db.VarChar(20) // info | warning | important
  deliveryMode        String   @db.VarChar(20)            // broadcast | event
  titleTemplate       String   @db.VarChar(200)
  bodyTemplate        String   @db.VarChar(1000)
  actionType          String   @default("none") @db.VarChar(20) // none | page | url
  actionValueTemplate String?  @db.VarChar(500)
  dedupeKeyTemplate   String?  @db.VarChar(200)
  variables           Json     @default("[]")             // 变量声明数组
  enabled             Boolean  @default(true)
  createdBy           String?  @db.VarChar(64)
  createdAt           DateTime @default(now())
  updatedAt           DateTime @updatedAt

  notifications       Notification[]

  @@index([type, enabled])
  @@index([deliveryMode, enabled])
}
字段说明
code全局唯一，创建后不可改；消息发送与事件生成都按编码取模板
variablesJSON 数组，每项为 { key, label, type, scope, required, example, fallback }，scope 为 global 或 user
dedupeKeyTemplate仅事件模板使用，渲染后写入通知的 dedupeKey
enabled停用后不可用于新消息；被通知引用时禁止删除，只能停用

8.2 Notification（消息）

model Notification {
  id           BigInt   @id @default(autoincrement())
  templateId   BigInt?
  template     NotificationTemplate? @relation(fields: [templateId], references: [id], onDelete: SetNull)
  templateCode String   @db.VarChar(60)   // 快照，模板删除后仍可追溯
  type         String   @db.VarChar(20)
  level        String   @default("info") @db.VarChar(20)
  title        String   @db.VarChar(200)  // 渲染后的标题
  body         String   @db.VarChar(1000) // 渲染后的正文
  actionType   String   @default("none") @db.VarChar(20)
  actionValue  String?  @db.VarChar(500)
  deliveryMode String   @db.VarChar(20)   // broadcast | event
  userId       String?                    // event 消息的收件人；broadcast 为 null
  user         User?    @relation("UserNotifications", fields: [userId], references: [id], onDelete: Cascade)
  variables    Json?                      // 变量值快照
  status       String   @default("draft") @db.VarChar(20) // draft | published | revoked
  isTest       Boolean  @default(false)
  publishedAt  DateTime?
  expireAt     DateTime?
  revokedAt    DateTime?
  dedupeKey    String?  @unique @db.VarChar(200)
  createdBy    String?  @db.VarChar(64)
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  reads        NotificationRead[]

  @@index([status, publishedAt])
  @@index([deliveryMode, status, publishedAt])
  @@index([userId, status])
  @@index([type, createdAt])
}

8.3 NotificationRead（用户已读）

model NotificationRead {
  id             BigInt   @id @default(autoincrement())
  notificationId BigInt
  notification   Notification @relation(fields: [notificationId], references: [id], onDelete: Cascade)
  userId         String
  user           User    @relation(fields: [userId], references: [id], onDelete: Cascade)
  readAt         DateTime @default(now())

  @@unique([notificationId, userId])
  @@index([userId, readAt])
}

model User {

  notifications     Notification[]     @relation("UserNotifications")

8.5 查询与清理

  • 用户可见消息：status = published 且 publishedAt <= now 且 expireAt 为空或大于 now，并且满足 deliveryMode = broadcast 或 userId = 当前用户。
  • 未读数：上述可见消息中，左连接 NotificationRead 后当前用户没有已读记录的数量；isTest = true 不计入正式统计。
  • 全站广播不预生成收件人行；只有用户真正阅读时才写 NotificationRead，避免广播产生 N 行冗余。
  • 去重依赖 dedupeKey 唯一索引；Postgres 允许多个 NULL，因此广播消息不受影响。
  • dedupeKey 渲染规则示例：pet_hungry:{petId}:{YYYY-MM-DD}，保证同一宠物每天最多一条。
  • 清理：每天删除 createdAt 早于 90 天且状态为 revoked 或已过期的消息，关联已读记录级联删除；草稿不自动清理。
  • 分页查询走 [deliveryMode, status, publishedAt] 索引，已读判断走 [notificationId, userId] 唯一索引。

9. 接口设计

9.1 通用约定

  • 后台接口前缀 /api/admin，使用 requirePermission(request, "notifications") 鉴权；没有权限返回 403。
  • 用户接口前缀 /api/app，使用 requireAppUser(request) 获取当前用户；Web 通过现有 /api/app/[...path] 代理访问，不新增代理。
  • 请求与响应使用 JSON，字段 camelCase；BigInt 统一序列化为字符串，避免前端精度丢失。
  • 分页参数 page 默认 1，pageSize 默认 20、最大 100；响应包含 items、total、page、pageSize。
  • 错误响应统一为 { "error": "错误说明" }，使用 400（参数错误）、401（未登录）、403（无权限）、404（不存在）、409（编码冲突或不可删除）、422（模板校验失败）。

9.5 事件消息生成

不新增对外 HTTP 接口，在 apps/admin/lib/notification.ts 提供内部方法：

  • renderNotification(template, variables)：校验并替换占位符，返回标题、正文、跳转地址与缺失变量；缺失必填变量时抛错。
  • publishBroadcast({ templateCode, variables, expireAt })：校验发送方式为 broadcast、变量均为 global，写入快照并发布。
  • createEventNotification({ templateCode, userId, variables })：校验发送方式为 event、渲染去重键，按 dedupeKey 幂等写入；重复触发直接返回已有记录。
  • generatePetHungryNotification(userId)：在 GET /api/app/pet 与 GET /api/app/notifications 中调用。先计算宠物状态，满足饥饿条件且当前时间在 08:00–22:00 时生成，去重键为 pet_hungry:{petId}:{YYYY-MM-DD}。

9.6 后台权限与导航
